How to measure, improve and ship the Orbita agent with Arize

The steps are in the order you do them. Six data steps come first, because evals only measure well on clean, defined data. Ten steps then build the measuring stick before a prompt reaches sellers. The last seven keep it honest in production and decide when a field may write on its own.

The two loops

Evals are two loops that feed each other. The offline loop decides whether a change is allowed to ship. The online loop finds what the offline loop does not know yet. Every arrow below is a skill you can run.

Offline: may this change ship?

Runs before every prompt, model or schema change
  1. Dataset of cases with expected answers (arize-dataset)
  2. Run the candidate on every case (arize-experiment)
  3. Score with code checks, then the validated judge
  4. Compare with the version in production
  5. Promote only if it passes the gate (arize-prompts)

Online: what are we getting wrong?

Runs all the time, reviewed weekly
  1. Every seller run is a trace (arize-instrumentation)
  2. Thumbs and judges score the traces (arize-annotation, arize-evaluator)
  3. You read the worst ones and name the failure (error-discovery)
  4. Each new failure becomes a dataset case
  5. That case now guards every future change

Both loops follow one rule from the course by Hamel Husain and Shreya Shankar. Read real traces before you write any automated check. A judge built on guesses only measures the guesses.

What "100% accuracy" can mean

"100%" is a fair goal when you say which 100%. There are three kinds, and only the first can be guaranteed.

1 · By construction (guaranteed)

A rule enforced in code holds on every run, because a wrong answer cannot get past it. Every quote must sit on the line it cites. Another seller's deal is blocked before the model. The stage moves one step at most, and seller-only fields are dropped. Nothing is written without approval or an Always-allow permission. Today 50 guardrail checks prove that each rule fails without its guard.

2 · On the eval set (a gate)

Sonnet 5.5 passed 11 of 11 in every run on schema v3. That is a gate the prompt must clear, not a property of the agent. The same prompt on Haiku 5.5 scored 10, 9 and 7 of 11 in three runs. One run proves little, so you need several.

3 · In production (measured, with a margin)

With zero failures in n cases, the true failure rate can still be up to about 3/n (the "rule of three", 95% confidence). Orbita has 9 cases that reach the model, so 9 of 9 only shows accuracy above about 67%. To claim 95% you need about 60 clean cases; for 99%, about 300.

4 · The backstop: the seller

Whatever the model gets wrong, the seller sees it before it is written, field by field, with the quote. So the honest promise is: every CRM write is either approved by a person or allowed by a rule they set. Evals shrink how often the seller has to correct; they do not replace the seller.

So the practical target has four parts. The code rules hold 100%. The eval set passes 100% across repeated runs. The production pass rate is measured on enough cases to mean something. The seller stays the last check.

Your questions, answered

Short answer first, then the detail. Open the ones you need.

How is the Error discovery app linked to my Arize account?It is not linked automatically. Both look at the same 11 cases, but each keeps its own labels.
  • Error discovery (eval/error_discovery/ and the CRM's Evals › Trace review) runs on your machine. It reads the committed runs in eval/outputs/ and saves your Pass, Fail and notes in annotations.json. Those runs were made without tracing, so they have no Arize trace id.
  • Arize receives the runs made with tracing on (eval/arize_runs/). Its review queue keeps its own labels.
  • The common key today is case + model (for example T9 on Sonnet 5.5). Arize links each of those runs to its trace.
  • What to do: label in one place. Arize is the better home once the app traces in production, because thumbs, judges and labels then sit on the same trace. To connect the two, the records need the trace id that pipeline.mjs now saves, plus a small script that copies the labels to Arize as trace_review and failure_mode. That folder belongs to the CRM's Evals session, so the change is theirs to make.
Which skill do I use, from beginning to end?Follow the steps on this page. Each one names its skill, and the full order is under "Skills, start to end".
  • Unsure where you are? Run /evals-start, which routes you. To check an existing setup, run /eval-audit.
  • The short version is data (D1–D6), then trace, read and name failures, code checks, dataset, experiments, judge, prompt versions, optimization, gate, production, autonomy.
  • See the table in order.
How do I promote a tier of autonomy?One field at a time, from Needs approval to Always allow, on measured evidence. You demote it again if Undo starts climbing.
  • Orbita's tiers are per field: Never, Needs approval, Always allow (written at once, with Undo).
  • A field moves up when it passes the offline gate and sellers approve it unedited many times in a row. About 60 approvals in a row back a 95% claim, and about 300 back 99%.
  • Step 17 has the full rule.
When the LLM judge shows a green check, can I assume it is right?No, not until the judge is validated. A green check is the judge's opinion. Its value depends on how often it agrees with you.
  • Validate first. You label about 20 Pass and 20 Fail runs yourself and compare. The judge must catch real failures (TPR) and pass good runs (TNR), both near 0.9. Our judge has said "supported" 18 times out of 18 and never Fail, so nobody knows yet how well it catches failures.
  • A green check covers only what the judge checks. evidence_supported looks for invented or changed facts. It does not look for missing ones. Those are the code checks' job.
  • After validation, keep reading about 10 green runs a week. Validate again whenever the judge's prompt or model changes. The course's validate-evaluator also corrects the observed pass rate for the judge's known errors.
Is the code judge better, and should it always come first?It should come first for anything a rule can decide. It is not better at everything: it checks only what you wrote rules for.
  • Code is free, instant and gives the same answer every time. If code already fails a run, you do not need to pay a judge to read it.
  • Code misses what nobody wrote a rule for. Our scorer has 80 "must include" rules and only 2 "must not include", so it rarely sees an invented fact. That is the judge's job.
  • The order is code checks, then the validated judge, then you read a sample. Each layer catches what the one before it cannot.
Can I compare answers side by side, like in Braintrust?Yes. In the dataset, open Experiments, select two or more, and click Compare.
  • The table view puts each case on a row, with each experiment's output, labels, cost and latency in its own column.
  • Diff Mode picks a baseline and highlights the labels that changed: the cases a change fixed or broke.
  • Diff Output Mode highlights text added, removed or changed against the baseline. It is in Arize's docs, but check the live screen if you cannot find the control.
  • The experiments pushed so far store the output as one long line of JSON, which is hard to read in a diff. push_experiment.mjs now writes one field per line, so future experiments diff cleanly.
  • To compare prompt versions rather than runs, use the Prompt Playground. It runs two versions on the same input, side by side.
  • Ready-made links: the Haiku and Sonnet comparisons and the five v4 setups.
How do I manage the skills and Arize from the terminal?Two installers, one Arize profile, and a monthly check. The commands are in "Manage the stack in the terminal".
  • Arize skills update with ax skills install --global --agent claude-code --yes --force. The course skills update with npx skills update -g.

Phase 0

Before evals: get the data ready

An agent reads data and writes data. If nobody has defined that data, checked it or decided who owns it, every eval measures the data's problems along with the agent's. These six steps come before you write the first prompt.

D1

Map the sources and their owners

Exists on Orbita

List every source the agent reads and every place it writes. Name one owner for each. When a number looks wrong, the owner is the person who can say whether the data or the agent is at fault.

What to write down
  • Source, format, who produces it, how often it changes.
  • What the agent reads from it and what it writes back.
  • The owner, and who may change the source's structure.
On Orbita
  • Reads: CRM clients and opportunities (data/), meeting transcripts and chats from the notetaker, the policies in policies/.
  • Writes: 22 opportunity fields, only through applyApprovedFields.
  • Suggested owners: sales operations for the CRM, whoever runs the notetaker for transcripts, the agent owner for policies.
D2

Build the catalog and the business glossary

Catalog exists, glossary has gaps

The catalog says what each field means, which values it accepts and who owns it. The glossary maps the words customers and sellers really say to those values. A model can only pick the right option if the option says, in plain words, what it covers.

Each field needs
  • A one-line definition and an example.
  • The allowed values, each with its own definition.
  • The everyday synonyms for each value.
  • An owner, and a sensitivity class (public, internal, personal).
On Orbita
  • agent/field_schema.json is the catalog: 22 fields, picklists since schema v4, permissions per field.
  • The gap: options have no synonyms. In T9 the customer asked for an "enrolment funnel per campus". Sonnet wrote that phrase in its own note but did not choose Pipeline management. That is a glossary gap, not a model gap.
Done when every picklist option has a definition and the words customers use for it, and each field has an owner.
D3

Measure data quality and set a baseline

Pre-checks in code; no baseline report

Before the agent runs, check that its input is complete, valid, unique, consistent and fresh. Write the numbers down. Without a baseline, every bad input looks like an agent failure.

CheckQuestionOn Orbita
CompleteIs anything missing?A recording much shorter than the meeting is marked Incomplete and stopped in code.
ValidIs each value allowed?Stage, picklists and amounts are checked against the schema by the validator.
UniqueIs anything duplicated?Two clients with near-identical names would send a meeting to the wrong deal.
ConsistentDo sources agree?The meeting's seller must own the opportunity, or the run is blocked.
FreshIs it current?A value that contradicts one the seller already approved always waits for the seller.

The pre-checks already enforce several of these per run. What is missing is the aggregate view: the share of meetings blocked as Incomplete, the duplicate rate and the staleness. The dashboard's "blocked runs by reason" panel (step 14) is the start of it.

D4

Agree data contracts and version them

Schema is versioned

A data contract fixes the shape of the data between who produces it and who uses it. Any change to the shape is a new version. A new version means the old eval results no longer apply, and the gate runs again.

Orbita showed this on 31 October. Schema v4 turned free text into picklists. Sonnet at the production setting dropped from 11/11 to 8/11 on the same cases. The contract change was the cause, and the gate caught it before it shipped. That is why every experiment is tied to one dataset version and one schema version.

D5

Treat key datasets as data products

Not formalized

A data product is a dataset someone owns, documents, versions and keeps to a quality promise, built for one use. The agent's input and its eval set are both data products. When nobody owns them, they drift.

Input product: opportunity context

The client, the opportunity and its meetings, joined and ready for the agent. Owner: sales operations. Promise: no duplicates, ownership correct, refreshed before each run.

Eval product: the eval set

The cases, their expected answers and a fixed held-out share. Owner: the agent owner, with sellers as the experts who settle disputes. Promise: every production failure becomes a case within a week.

D6

Classify personal data, set access, keep lineage

Partly built

Mark which fields hold personal data. Decide who may see each source, how long it is kept and where it flows. Then make every write traceable back to its source.

  • Personal data: transcripts name customer-side people. Traces copy them to Arize unless ORBITA_TRACE_HIDE_IO=1.
  • Access: a seller can only update their own deals. The check runs in code before the model.
  • Lineage: each write is in the activity log with its run id and quote, and Always-allow writes can be undone.
  • Retention: 90 days and deletion on request are written in the PRD but not built yet (see step 16).

What happens when the data steps are skipped

The symptoms show up in the evals, but the causes sit in the data. The team then tunes prompts to fix problems no prompt can fix.

SkippedWhat you see in evalsOrbita example

The input passes the five quality checks, and you know the numbers. The schema has a version. The eval set has an owner and a held-out share. Personal data is marked, and access is checked in code.
Phase A

Before production: build the measuring stick

1

Trace every run

Done today

Without traces you can only see the final answer. With them you see what the agent read, what the model answered, and what the validator corrected, for every run, kept for later.

arize-instrumentation
What we did
  • New file agent/tracing.mjs, following Arize's Anthropic guide for Node: OpenTelemetry 3 plus the OpenInference Anthropic instrumentor, sent to otlp.arize.com (US, matching your account).
  • One trace per run: orbita.update → pre-checks → Anthropic Messages → validator. The validator span keeps the model's raw answer apart from the corrected one.
  • Each trace carries the run id, case, model, effort, cost and prompt_version (a hash of the system prompt), so the dashboard can split any metric by prompt version.
  • Off unless ARIZE_SPACE_ID and ARIZE_API_KEY are set. Nothing changes for the kit or the tests without them.
Watch out
  • Traces hold the transcript, which is personal data of customer-side people. Set ORBITA_TRACE_HIDE_IO=1 when real customers are involved, and list Arize in the data processing agreement.
  • OpenTelemetry 3 takes new BatchSpanProcessor({ exporter }), not the exporter itself. The old form crashes at the first flush.
  • A CLI must flush before it exits, or the last spans are lost.

Put every objective check in code

Done today

Anything a rule can decide (status, format, a fact present, a quote on its line, a forbidden value) belongs in code: free, instant and never inconsistent. An LLM judge is only for what needs interpretation.

The kit already had the scorer (eval/score.mjs). The new script eval/arize/push_code_checks.mjs runs it on a traced run and writes each verdict to Arize as the code_checks label on that run's root span, with the failed checks as text. Sonnet passed 11 of 11; Haiku 7 of 11 on the same run.

5

Build the dataset

Started: 11 cases, needs more

A dataset is the fixed set of cases every change is tested on. Each example holds exactly what the agent reads and the expected answer. It grows every time production shows a new failure.

arize-datasetgenerate-synthetic-data

Dataset orbita-eval-cases: the 11 test conversations, each with the exact message the agent reads for that case (CRM context plus numbered conversation), the expected outcome from eval/expected_results.json, and whether code blocks it before the model.

What is missing
  • Held-out cases: conversations never used to tune the prompt. Without them, a prompt can learn the test.
  • Volume: 9 cases reach the model. For a 95% claim you need about 60 (see "What 100% can mean").
  • Real failures: every Fail from step 3 and every thumbs-down from step 12 should become a case.
How to grow it
  • Use generate-synthetic-data with dimensions taken from your failure modes (channel, MEDDPICC coverage, speaker naming, language, length).
  • Keep a fixed 30% of new cases as held-out, never shown to the optimizer.
  • Version the dataset; experiments are tied to one version.

Add one LLM judge, then prove it

Created, not validated

A judge is a second model that grades the agent on something code cannot check. Build it for one failure you have actually seen, with Pass or Fail only, and trust it only after it agrees with your own labels.

write-judge-promptarize-evaluatorarize-ai-provider-integrationvalidate-evaluator
What we did
  • Evaluator evidence_supported in Arize: "is every proposed value supported by what the speakers said?" Same definition as the local judge in eval/judge.mjs, so there is one judge, not two.
  • Judge model Sonnet 5.5 through the Anthropic integration already in your space (no key handled here), temperature 0, with explanations.

10

Pass the gate, then promote

Your decision

Promotion is a decision with written criteria, not a feeling after one good run. Agree the gate once, then apply it to every change: prompt, model, schema or effort.

  • Code checks 100% on the full dataset, 3 runs per model
    Repeated runs, because one run hides flakiness. Today Sonnet meets this on the current prompt (2 runs) and the candidate (1 run).
  • No regression
    Every case that passes in production also passes with the candidate (the experiment compare view shows flips).
  • Held-out cases pass at least as well as before
    Cases never shown to the optimizer. Missing today: this is what keeps the v2 candidate in staging.
  • The judge is validated, then clean
    TPR and TNR near 0.9 on held-out human labels; then "supported" on every run.
  • Cost and speed inside budget
    Today Sonnet costs about US$ 0.028 per conversation, with a median of 14 s from the logs. Set the ceiling in the PRD and check it in the experiment.
  • You read 10 new outputs yourself
    Numbers miss what a careful seller notices. Ten minutes in the trace view.

When all six hold: merge the prompt change into the files, run the tests, move the production label to the new Hub version, and note the new prompt_version in the PRD. To roll back, move the label and revert the merge.

Send seller thumbs into Arize

Wired, waiting for real ratings

A thumbs-down tells you that something failed, on real work, at no cost. Linked to its trace, it tells you exactly which run to read.

The weekly review

A 30-minute habit

The loop only turns if someone turns it. Thirty minutes a week, same order every time:

  1. Read the dashboard: did any panel move?
  2. Read every thumbs-down trace from the week, and 10 random traces.
  3. Label them (step 3). New failure? Name it and count it.
  4. Turn each new failure into a dataset case with the expected answer (step 5).
  5. Pick the biggest failure mode: fix it in code if a rule can, otherwise in the prompt (step 9).
  6. Run the gate (step 10) before anything ships.

Promote a field's autonomy

Rule to agree

Autonomy in Orbita is set per field, not for the whole agent. A field earns more autonomy with evidence, one field at a time. It loses autonomy as soon as sellers start undoing it.

Tier 0
Never

The agent leaves the field alone. For fields the business wants only people to set.

Tier 1
Needs approval

The agent proposes, with the quote, and the seller approves, edits or rejects. This is where every field starts and where evidence is collected.

Tier 2
Always allow

Written at once, with Undo. Today: Summary, Objections and Commitments.

Move a field up from Needs approval to Always allow when all five hold

  • It passes the offline gate for that field
    The field's code checks pass on every case in 3 runs, held-out cases included, on the production model and effort.
  • Sellers approve it unedited, many times in a row
    About 60 approvals in a row without an edit back a 95% claim, and about 300 back 99% (rule of three). One edit restarts the count.
  • A mistake is cheap and reversible
    Start with text fields. Keep the fields that move forecast numbers (amount, close date, stage) on approval the longest.
  • Its validated judge is clean on that field
    For fields where code cannot check meaning, the judge must be validated (step 7) and say "supported" on recent runs.
  • The field's owner signs it off, in writing
    The owner from the catalog (D2) and the sales manager. Write the date and the evidence in the PRD.
Move it back down when
  • Undo on that field passes 5% over two weeks.
  • A new failure mode touching the field appears in the weekly review.
  • The prompt, model or schema changes. The field returns to Needs approval until the gate passes again.
Where the evidence comes from
  • The activity log records each field_decided event (approve, edit, reject, or written by Always allow) and each Undo.
  • A small script could count approvals in a row and the Undo rate per field, and send them to Arize as annotations. It is not built yet.

Glossary

Trace
Everything that happened in one agent run, as a tree of steps.
Span
One step in a trace: the pre-checks, the model call, the validator.
Session
Traces grouped by a shared id. Here, one eval run of one model.
Annotation
A label a person or a script puts on a span: thumbs, Pass or Fail, a note.
Evaluator
A judge definition in Arize: an LLM prompt with fixed labels, or Python code.
Task
What runs an evaluator on real data: once (backfill) or on every new span (continuous).
Dataset
The fixed cases every change is tested on, with expected answers.
Experiment
One version of the agent run on every dataset case, each run scored.
Prompt version, label
An immutable saved prompt, and a movable pointer (production, staging) to one of them.
Failure mode
A named, counted kind of mistake found by reading traces.
Held-out case
A case never used to tune the prompt, so it can show whether a fix generalizes.
TPR, TNR
Of the real failures, the share the judge catches. Of the good runs, the share it passes.
Data catalog
The list of fields with definition, allowed values, owner and sensitivity.
Business glossary
The everyday words mapped to the values the system stores.
Data contract
The agreed, versioned shape of data between its producer and its user.
Data product
A dataset with an owner, documentation, a version and a quality promise.
Lineage
The record of where a value came from and where it went.
Autonomy tier
A field's permission: Never, Needs approval or Always allow.
